# Persistent local GATE services

These user-service templates keep the loopback observer, one or more typed
campaign workers, and an optional remote cockpit runner running in Linux or
WSL2. The campaign service calls only
`gate campaign worker`; that worker consumes immutable typed jobs, writes an
owner-only heartbeat, and retains the controller's existing authority checks.
It does not turn cockpit or model text into a command.

## Prerequisites

- Node.js must meet the version in `package.json`.
- `GATE_HOME` must be a private local directory already initialized by GATE.
- The selected case and campaign must already exist. Creation starts a campaign
  paused; run `gate --case CASE campaign resume CAMPAIGN` when it should run.
- Linux must provide the protected system `flock` used by the controller.
- The remote-runner unit additionally requires a completed `remote init`, the
  generated owner-only `runner.env`, an authenticated dedicated Codex home,
  and the protected pinned Codex executable described in
  [remote cockpit](../../../docs/remote-cockpit.md).

For WSL2, enable systemd in `/etc/wsl.conf`, then restart the distribution from
Windows with `wsl --shutdown`:

```ini
[boot]
systemd=true
```

After WSL restarts, enable user lingering once so the user manager is not tied
to an open terminal:

```bash
sudo loginctl enable-linger "$USER"
```

Lingering does not start a stopped WSL distribution and cannot keep Windows
awake through sleep, reboot, or `wsl --shutdown`. If unattended restart after a
Windows boot is required, add a Windows Task Scheduler entry that starts this
distribution; the enabled user units then start inside it.

## Render and configure

From a trusted GATE checkout, render fixed absolute Node and repository paths:

```bash
node deploy/local/systemd/render.mjs \
  --repo "$PWD" \
  --node "$(command -v node)"
```

Create the common owner-only environment file. Systemd environment files do
not use shell expansion, so enter the literal absolute path that was used when
the cases and remote bundle were created. The example below is GATE's default
POSIX path; use the same custom `GATE_HOME` everywhere if you changed it:

```bash
install -d -m 700 "$HOME/.config/gate"
cat >"$HOME/.config/gate/gate.env" <<'EOF'
GATE_HOME=/home/USER/.local/share/gate
EOF
chmod 600 "$HOME/.config/gate/gate.env"
```

Each service instance has a short local instance label and a separate private
file. This permits the same campaign ID in different cases:

```bash
cat >"$HOME/.config/gate/campaign-first-pilot.env" <<'EOF'
GATE_CASE=CASE_ID
GATE_CAMPAIGN=CAMPAIGN_ID
# Set this for a campaign whose initial queue contains confirmed lab HTTP jobs.
# Adaptive jobs already carry the authority binding in their enqueue permit.
# GATE_LAB_AUTHORITY=AUTHORITY_ID
EOF
chmod 600 "$HOME/.config/gate/campaign-first-pilot.env"
```

Load and start the observer and worker:

```bash
systemctl --user daemon-reload
systemctl --user enable --now gate-observer.service
systemctl --user enable --now gate-campaign@first-pilot.service
```

Inspect their exact lifecycle and output with:

```bash
systemctl --user status gate-observer.service gate-campaign@first-pilot.service
journalctl --user -fu gate-observer.service
journalctl --user -fu gate-campaign@first-pilot.service
```

## Optional persistent remote runner

The remote runner has no JSON config flag; its reviewed interface is the exact
`GATE_REMOTE_*` environment generated by `remote init`. Copy that generated
file into the user service configuration and add only the protected executable
search path. Set `gate_home` below to the same literal absolute `GATE_HOME`
written in `gate.env`. Keep the generated source file and the installed copy
owner-only:

```bash
gate_home=/home/USER/.local/share/gate
runner_state="$gate_home/remote/CASE_ID/runner"
service_environment="$HOME/.config/gate/remote-runner-first-pilot.env"
install -m 600 "$runner_state/runner.env" "$service_environment"
# Set the existing GATE_REMOTE_EXECUTION_MIRROR line in this installed file to
# 1 for this case when the authenticated cockpit should receive the bounded
# operational mirror. The running unit reads this copy, not runner_state.
cat >>"$service_environment" <<'EOF'
PATH=/opt/codex-0.159.2/bin:/opt/nodejs/node-v24.19.0-linux-x64/bin:/usr/bin:/bin
EOF
chmod 600 "$service_environment"

systemctl --user daemon-reload
systemctl --user enable --now gate-remote-runner@first-pilot.service
systemctl --user status gate-remote-runner@first-pilot.service
journalctl --user -fu gate-remote-runner@first-pilot.service
```

The instance name is only a local label. The owner-only environment carries
the exact case, session revision, runner identity, state paths, and coordinator
origin. The unit invokes the same reviewed runner entrypoint as
`npm run cockpit:remote:runner`, without using npm as the service supervisor.
It contains no credential, case, path, or target value in the public unit.

The runner already retries transient coordinator failures with bounded
backoff. Its unit uses `Restart=on-abnormal`: a signal, core dump, watchdog, or
timeout restarts, while a clean stop or permanent configuration, identity,
signature, boundary, or session-revision rejection remains stopped for review.
Never enable two runner instances that point at the same journal.

`Restart=on-failure` handles observer and campaign-worker process crashes. A clean operator stop or
`systemctl --user stop` remains stopped. A completed queue stays alive and
waits for a verified adaptive enqueue until the operator stops it. The worker obtains one
kernel-backed singleton lease, checks for an interrupted running job on start,
and uses the controller's recovery path before scheduling more work. Its
heartbeat is stored beside the private campaign state. The observer projects
the bounded worker-backed pilot state to the cockpit while its exact generation
and kernel lease remain live; expiry or process loss downgrades it to
unavailable.
